# Transfer functions: normalized sRGB and Rec.709 slices

## Summary and question addressed

This module asks how normalized sRGB encoding differs numerically and semantically from the BT.709-6 source encoding curve. It retains the original sRGB reference and adds a separate Rec.709 oracle with explicit mathematical input and output domains. An inverse source curve, a reference display response and a camera log curve serve different purposes. A file or camera label alone is insufficient to select one of these operations.

The executable references accept finite normalized scalars. The Rec.709 inverse deliberately rejects the small unreachable interval introduced by the published rounded forward constants. That policy is useful for studying those equations, but unsuitable as a general quantized-video decoder. Same-number comparisons illustrate different encodings; they do not predict equal appearance or establish better image quality. The parent topic remains research-draft: full HDR/log coverage, extended domains, precision comparisons, actual camera/file semantics, licensing and app adoption still require separate work. No Perception Editor behavior or private media is changed or assessed here.

## Evidence and scope

[I] sRGB definitions retain SRC-PB001-01/02, which are secondary summaries of IEC 61966-2-1; the IEC text was not obtained, so those claims are inferred and graded D. [V] BT.709-6 §1 item 1.2 defines the source curve, with §3 item 3.1 describing primary-signal pre-correction. BT.1886 Annex 1 concerns display response. Panasonic's Varicam manual separately specifies V-Log; it does not establish original S5 behavior. Exact editions and scope are in [sources](../../references/sources.md).

## Definitions, units and prerequisites

`L_s` and `C_s` are dimensionless normalized linear-light and encoded sRGB components. `L_r` and `V_r` represent normalized linear source input and corresponding Rec.709 signal. All have nominal domain [0,1] here. Equal numeric `L_s` and `L_r` are a controlled mathematical comparison, not a claim that their reference image states or physical scenes match. Primary conversion, white-point adaptation, alpha, luma/chroma conversion, legal-range coding and quantization are separate operations. No completed-topic prerequisite is needed to understand these scalar definitions.

## Mathematical foundations and derivations

### Preserved sRGB reference

Forward (CLM-PB001-01), inverse component transfer (CLM-PB001-02):

\[
C_s(L_s)=\begin{cases}12.92L_s,&L_s\le0.0031308\\1.055L_s^{1/2.4}-0.055,&L_s>0.0031308,\end{cases}
\qquad
L_s(C_s)=\begin{cases}C_s/12.92,&C_s\le0.04045\\((C_s+0.055)/1.055)^{2.4},&C_s>0.04045.\end{cases}
\]

The [sRGB oracle](../../experiments/srgb/reference.py) and [PB-001 vectors](../../tests/test_srgb.py) keep the original scope; PB-009 corrected six literal vectors, made `encode_srgb(1.0)` exactly 1 and tightened input validation without changing the equations. Rounded knees require nonzero round-trip tolerances. [I] With these constants the forward curve is very slightly discontinuous at `L_s = 0.0031308`: the upper branch starts about `2.85e-8` below the linear branch's end, so the forward function is monotonic except for that one downward step. The inverse jumps up by about `2.33e-9` at `C_s = 0.04045`.

### BT.709-6 source encoding

CLM-PB002-01, source item 1.2:

\[
V_r=f(L_r)=\begin{cases}4.5L_r,&0\le L_r<0.018\\1.099L_r^{0.45}-0.099,&0.018\le L_r\le1.\end{cases}
\]

[I] Algebraically, the linear branch reverses to `V_r/4.5`; the power branch reverses to `((V_r+0.099)/1.099)^(1/0.45)`. The lower branch approaches `0.081`, while the upper branch starts at `h=1.099*0.018^0.45-0.099 ≈ 0.08124794403514048`. Thus the exact rounded forward function has range `[0,0.081) ∪ [h,1]` and leaves a gap (CLM-PB002-02).

[D] This contribution defines a partial inverse on that range only:

\[
g(V_r)=\begin{cases}V_r/4.5,&0\le V_r<0.081\\((V_r+0.099)/1.099)^{1/0.45},&h\le V_r\le1.\end{cases}
\]

Inputs in `[0.081,h)` are rejected. This is a research-oracle policy (CLM-PB002-03), not a standard-mandated decoder behavior. Floating-point endpoints use the computed `h`; the range statement above describes the real-number equations.

### Distinguish the operation's role

| Operation | Input → output | Use and boundary |
| --- | --- | --- |
| BT.709 source OETF `f` | Normalized linear source → signal | Encoding reference above |
| Partial inverse OETF `g` | Reachable signal → source-domain value | Algebraic research reference; not display luminance or a general decoder |
| BT.1886 display EOTF | Normalized signal → screen luminance | Annex 1 includes screen black/white parameters and exponent 2.4; not implemented here |
| V-Log | Scene-linear reflection ↔ camera log signal | Panasonic manual §3 supplies separate equations; no implementation or S5-mode claim here |

[I] Inverting a source function does not select a display response or undo creative source processing. [D] Caller metadata/contracts must establish source image state, transfer, range and intended operation before choosing an oracle. Unknown camera internals stay unknown.

## Parameters, ranges, estimation and uncertainty

No fitted parameters. All reference arithmetic is scalar Python float/binary64 on the recorded host. PB-002 reachable-output round-trip tolerances are absolute `1e-14`; this is a test policy, not a perceptual bound. Since PB-009, both modules' literal vectors are correctly rounded Decimal values for the exact binary float input, checked within the measured maximum implementation error (sRGB 5 ulp encode / 7 ulp decode; Rec.709 3 ulp encode / 5 ulp inverse; previously absolute `1e-14`). Errors inside those bounds are accepted by design; a literal re-derivation test guards the literals; `1e-8` linear round trips and `1e-7` encoded round trips are unchanged. No float16/GPU parity or every-platform guarantee follows.

## Reference algorithm and pseudocode

For encoding: validate finite normalized input; choose the source-defined branch; evaluate and return an unquantized float. For partial inversion: validate; use the linear branch below 0.081; reject below computed `h`; otherwise evaluate the inverse power. [D] Keep the calculated inverse on its selected branch: cap the lower result at the float immediately below 0.018, and bound the upper result to at least 0.018. This prevents rounding from changing the branch during re-encoding; it does not accept gap values or clip invalid inputs. See [Rec.709 reference](../../experiments/rec709/reference.py). Each scalar costs O(1) work/storage; N components require O(N) work. No image buffers or app framework are prescribed.

## Edge cases, failure modes and safeguards

- [D] NaN, infinities, negatives and above-one inputs raise `ValueError`; clipping/extended-domain policy is deferred. Since PB-009, any `numbers.Real` except `bool` is accepted and converted once with `float()`; `bool`, `Decimal` (not registered as Real), `str`, `complex` and other types raise `TypeError`, and `-0.0` is treated as `0.0`.
- [I] A quantized level can fall in the rounded gap. For example, `(135-64)/876 ≈ 0.0810502283` uses BT.1886's nominal 10-bit normalization and lies inside it. The partial inverse intentionally rejects this case. A real decoder needs a separately reviewed policy.
- [I] Using the inverse OETF as a display EOTF gives the wrong operation semantics. Likewise, applying one transfer twice, confusing integer code/range normalization, or treating alpha as color are caller errors a scalar value cannot identify.
- [U] A particular file's transfer/image state cannot be inferred from these equations; inspect metadata and provenance. This contribution makes no sensor-RAW or original S5 output claims.
- Tests exercise both source branches, the exact input knee, gap rejection, invalid values, round trips on generated reachable outputs and signal-boundary round trips at both sides of the gap. Without inverse branch preservation, one-unit-last-place errors in linear output can become about 0.000247944 signal error at this discontinuity. Dense grids are sampled checks, not exhaustive floating-point proofs. The sRGB forward-knee step is now tested explicitly (PB-009).
