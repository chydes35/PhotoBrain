# Transfer functions: normalized sRGB slice

## Summary and question addressed

This first slice answers one question: how should a scalar reference convert a normalized linear-light sRGB component into encoded sRGB, and back? It supplies a mathematical contract, independent numerical vectors, and executable checks. This is useful when distinguishing storage encoding from a linear working value. It does not define a complete color-management pipeline, identify a camera's file encoding, or assess Perception Editor's current implementation.

Only finite components in [0,1] are accepted. Inputs outside that interval are rejected so that an experiment cannot silently discard highlights or negative values. That boundary is a local engineering decision. The broader transfer-functions topic remains research-draft: Rec.709, HDR, camera log and extended-range behavior still need their own evidence and contracts. Tests establish this scalar reference's stated behavior; they do not demonstrate production image quality, camera accuracy or GPU agreement.

## Evidence and scope

[V] The forward definition is grounded in the ICC encoding registry; the inverse is checked against the pinned W3C definition. See [the source registry](../../references/sources.md). Full IEC normative text was not obtained. [D] This reference narrows the domain to normalized components and does not implement W3C's extended negative-domain behavior.

## Definitions, units and prerequisites

`L` is a dimensionless normalized linear-light component; `C` is its dimensionless encoded component. Both use [0,1]. Treat RGB channels independently. Neither variable is an electron count, scene-radiance measurement or integer code. The transfer does not change primaries or white point. This slice contains its own mathematical definitions and has no completed-topic prerequisite; colorimetric context remains outside scope.

## Mathematical foundations and derivations

Forward encoding (CLM-PB001-01):

\[
C(L)=\begin{cases}12.92L,&L\le0.0031308\\1.055L^{1/2.4}-0.055,&L>0.0031308.\end{cases}
\]

Inverse component decoding (CLM-PB001-02):

\[
L(C)=\begin{cases}C/12.92,&C\le0.04045\\((C+0.055)/1.055)^{2.4},&C>0.04045.\end{cases}
\]

[I] Rearranging the upper forward branch gives `(C+0.055)/1.055 = L^(1/2.4)`; raising both sides to 2.4 yields the inverse power branch. The rounded knees differ slightly, so these published piecewise definitions are not exactly inverse at the join. The code preserves their constants instead of fitting a new curve.

## Parameters, ranges, estimation and uncertainty

No parameters are fitted. Numeric oracle: Python float/binary64 behavior on the recorded host. Tests allow absolute error `1e-14` against independently calculated literal vectors; round-trip tolerances are `1e-8` in linear components and `1e-7` in encoded components. These are scoped test policies, not a claim about perceptual error, float16 or every platform.

## Reference algorithm and pseudocode

Validate one finite scalar in [0,1]; select the branch by its input-domain knee; evaluate that branch; return an unquantized float. See [reference.py](../../experiments/srgb/reference.py). Per component, computation/storage are O(1); an N-component image costs O(N). No image buffers or runtime framework are prescribed.

## Alternative methods and comparative evidence

[I] A single power curve does not reproduce this piecewise reference. LUTs and GPU implementations are candidates for later comparison against the oracle; no speed or quality advantage is measured here.

## Edge cases, failure modes and safeguards

[D] NaN, infinities, negative and above-one values raise `ValueError`. Clipping, signed extensions and gamut mapping need explicit caller contracts. Encoding already-encoded data is a semantic error that a scalar cannot detect. Integer code normalization is the caller's responsibility; alpha must not be treated as a color component by assumption. Tests straddle both knees, exercise all 256 normalized 8-bit inputs, and check a dense grid. The forward knee has a tiny downward jump from rounding; grid monotonicity is not a proof of strict global monotonicity or exact round trips.

## Panasonic LUMIX-specific notes

Not camera-specific. [U] This contribution establishes no S5 RAW/JPEG profile, transfer or mode behavior; inspect actual file metadata and decoding semantics before applying it.

## Video/cinema extension

Deferred. Do not substitute this transfer for Rec.709, a display EOTF, PQ, HLG or V-Log without establishing signal semantics.

## Implementation notes for software

Use a generic explicit encoded/linear input contract. Before Editor adoption, inspect its current commit, working space and existing operators. App-specific tickets and color decisions belong to that repository; this oracle imports no app code. Do not multiply an already full-range integer code by 255 again, or confuse this scalar transfer with an input camera profile.
